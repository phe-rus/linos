## Summary

The change implements signed, bounded A/B image staging and a deployment-bound development guest health protocol. Signature verification, active-slot preservation and firmware counter handling are carefully separated, and the documented exclusions match the development-only scope. Two health-intent persistence cases prevent the promised interrupted-approval and fallback reconciliation from completing.

## Major

### 🟠 A failed blessing intent permanently prevents exhausted fallback reconciliation, `system/src/recovery/update/health.rs:495`

**Problem**: Candidate approval writes `action=good` before calling the native blessing helper at lines 433–434. If the helper fails or the process exits before renaming the counted entry, this intent remains. Once firmware exhausts the candidate, fallback calls `record(..., "rollback")`, which refuses that same deployment's existing `good` intent as conflicting at lines 341–343.

**Why it matters**: Reproduce with the existing health fixture: run candidate settlement with a blessing closure that returns an error without renaming; rename `linos-2-b+1-1.conf` to `linos-2-b+0-2.conf` to represent the exhausted second trial; then settle the fallback boot. It returns `Conflicting or stale health intent` instead of `RolledBack`, and every subsequent fallback boot leaves the journal stuck in Trial. A process interruption between durable approval intent and native blessing causes the same outcome. This affects the explicitly supported development guest protocol, independently of physical power-loss qualification.

**Suggested fix**: Allow an exhausted, verified candidate counter and matching fallback identity to supersede an uncompleted `good` intent for the same deployment, while continuing to refuse unrelated transaction intents and blessed candidates. Persist that transition atomically. Add a regression covering failed/interrupted native blessing followed by exhausted fallback, including repeated reconciliation.

### 🟠 Publishing health intent directly under its authoritative name strands interrupted writes, `system/src/recovery/update/health.rs:347`

**Problem**: `record` calls the general `write_new` helper directly on `health-intent`. That helper creates the final file before writing and syncing its contents. A process exit after creation but before the write leaves an empty authoritative file; an interrupted or failed write can leave a partial file. Future calls reject that file as a conflicting or stale receipt, with no recovery path.

**Why it matters**: Reproduce a process interruption immediately after `create_new("health-intent")` succeeds, or emulate its observable state by creating an empty `health-intent` in the existing fixture before candidate settlement. The viable candidate cannot approve on either remaining attempt, and exhausted fallback also cannot record its rollback intent. The journal's pending-file protocol already avoids this failure, but health intent does not. This contradicts the guest contract that an interruption between approval steps can retry.

**Suggested fix**: Write intent to a non-authoritative pending name, sync it, atomically publish it and sync the state directory. Retry should safely discard an interrupted pending file without accepting malformed authoritative receipts. Cover interruption before publication and a write failure as well as the existing interruption after native blessing. Consider the same direct-write window in the host `activated` receipt when implementing the persistence helper.

## Resolution review, 22 November 2026

Both original major findings are resolved in the inspected source. The original findings and coverage assessment above describe the first review snapshot.

- `record` permits replacement of a `good` intent only when its bytes match the exact current deployment and the requested action is `rollback`. Its sole rollback caller first validates the running fallback identity, exhausted candidate counter, absence of a stable candidate entry and matching journal transition. Failed blessing can therefore reconcile to the old healthy slot without relaxing deployment checks.
- Intent is written and synced at `.health-intent.pending`, then renamed to the authoritative name and followed by a directory sync. Interrupted pending files are discarded on retry. Replacing approval with rollback keeps the previous valid approval authoritative until publication succeeds.
- A differing deployment intent remains rejected: the replacement exception compares the complete encoded current-deployment `good` receipt, including transaction, trial generation, release and candidate slot. Malformed authoritative receipts also continue to fail closed.
- Three added regression tests exercise failed native blessing followed by exhausted fallback, an interrupted pending initial approval, and an interrupted pending rollback that preserves its existing approval until retry.

**Remaining blockers or major findings**: None identified in the reviewed fixes. This was source-only follow-up review; no builds, tests or VMs were run by this reviewer. Regression execution remains the parent agent's validation responsibility.

### 🟡 Successful CI discards the resource measurements, `.github/workflows/kernel-integration.yml:125`

**Problem**: `run_phase` redirects the actual metrics and pressure output into the retained fixture's `expect-verify.log`, and emits only a phase summary to its caller. The workflow's `tee` consequently does not capture those measurements. Its EXIT trap deletes the entire fixture, and the artifact step runs only on failure and does not include the successful fixture's logs.

**Why it matters**: On a successful qualification run the checks execute, but the recorded MemTotal, MemAvailable, SwapTotal, SwapFree and pressure result disappear. The resulting CI run cannot supply the numerical evidence needed to assess or compare the resource check.

**Suggested fix**: Preserve a compact metrics and pressure result outside the disposable fixture before deleting it, and upload that small evidence file or write it to the job summary on successful runs. Avoid retaining the large disk or unnecessary account interaction logs.
